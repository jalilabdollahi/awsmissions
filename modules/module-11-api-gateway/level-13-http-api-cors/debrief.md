# Debrief: HTTP APIs make CORS a setting, REST APIs make it a project

Compare with the REST API CORS mission: there you assemble an OPTIONS method, a MOCK integration and header mappings by hand, twice (preflight and real response). On an **HTTP API (v2)** the same result is one object:

```
CorsConfiguration:
  AllowOrigins, AllowMethods, AllowHeaders, ExposeHeaders, MaxAge, AllowCredentials
```

When it is set, API Gateway intercepts `OPTIONS` requests for every route (you do not even need an OPTIONS route), answers them with 204, and appends the `Access-Control-*` headers to real responses. Two consequences:

- Your Lambda's own CORS headers are **ignored or overwritten** once the API has a CorsConfiguration, so do not set them in both places and wonder which wins.
- If no CorsConfiguration exists, API Gateway adds nothing, and an OPTIONS call to a route you did not define is a 404 or 405: the browser blocks the actual request, and the console shows only a CORS error.

Rules the browser enforces, which explain this level's code review:
- With `AllowCredentials: true` the origin must be explicit. `*` is refused for credentialed requests, and so are wildcard methods/headers (the spec treats `*` literally when credentials are used).
- `MaxAge` lets browsers cache the preflight (up to 600 s here, but Chrome caps at 2 h and Firefox at 24 h). A low value means one extra OPTIONS request for every real request.
- Wildcard subdomains are not supported in `AllowOrigins` for HTTP APIs: list origins explicitly, per environment.

CORS is a browser feature, not access control. `curl` ignores it, so keep authorizers on the routes. Also remember that responses generated by API Gateway for failed authorization or throttling carry the CORS headers on HTTP APIs, which makes debugging easier than on REST APIs.
