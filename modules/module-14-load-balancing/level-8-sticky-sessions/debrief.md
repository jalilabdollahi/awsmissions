# Debrief: stickiness is a workaround, so know its limits

With stickiness enabled the ALB adds a cookie (`AWSALB`) to the first response. Requests that send the cookie back go to the same target, as long as that target stays healthy and the cookie has not expired. Two cookie flavours exist: **lb_cookie** (generated by the load balancer, you set only the duration) and **app_cookie** (the application's own session cookie names the session, and the ALB maps it to a target).

**It fixes the symptom, not the design.**
- If the sticky target dies, scales in, or fails health checks, the shopper moves to another server and loses the in-memory cart anyway.
- Sticky traffic can unbalance load: a few heavy users keep hammering one instance, and a new instance only gets new sessions.
- Deregistration delay and instance refresh interact with stickiness; sessions are only drained, not migrated.

**Better long-term**: keep session state outside the web tier (ElastiCache/Redis, DynamoDB) so any instance can serve any request. Then switch stickiness off again.

**Operational notes**
- Stickiness is configured per target group. With weighted target groups you also need target-group-level stickiness in the forward action so a client does not flip between groups.
- Clients that drop cookies (some API clients, health probes, curl without `-b`) are balanced normally. That is why the check also confirms new visitors are still spread across both servers.
- Pick the duration to match the session lifetime; one day is a sane upper bound for shopping carts.
